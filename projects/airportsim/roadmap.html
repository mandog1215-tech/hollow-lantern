Completed on the development line — merges last in the integration sequence

WP-03 — Development Mode

Five stages integrated the F3 diagnostic overlay, state identity, invariant status, delay explanation, trace inspection, snapshot capture/compare, and measured step cost. Non-interference was tested with trace enabled and disabled, including a planted-draw negative control. Snapshot hashing was measured at about 1.95 ms, so full identity refresh is on demand rather than placed in the normal frame path.

Qualification: the integrated full gate exited 2. Matched base/current comparisons reproduced the business-window and topbar-overlap failure signatures, supporting attribution as pre-existing defects; this does not turn the original gate into a pass. Both signatures were later addressed in the integration: the top-bar overlap is fixed (PR #13, merged) and the nondeterminism behind the intermittent business-window failures is fixed by seeding the test worlds (PR #13 merged; PR #11 pending); the remaining cosmetic truncation of long airline names in the Business window stays open as issue #14.

Completed on the development line — evidence recorded through 2026-11-02

WP-04 — Performance baselines

A measured step-cost model was recorded: fixed overhead, active-aircraft count, and simulated time step. The fit is useful as a baseline, not yet a license to optimize: the aircraft-count coefficient is weakly identified because long-run windows confound world age with aircraft count. Performance budgets are accepted for future comparisons (owner-accepted 2026-11-02: step cost at or below 45 µs against a measured median of 14.1 µs per call; at or below 1.7 s per simulated clock-day against a measured 0.56 s); no unmeasured largest-hub performance claim is made.

The integration, drawn. Nine packages are in; the sequence ends only when the final full gate passes on everything together. Until then, nothing on this page calls the integration complete.

Next — first after integration · Owner-authorized 2026-11-02

The save/reload continuation investigation (issue #15)

A reloaded game continues slightly differently from one that was never interrupted. The divergence is measured, not anecdotal: it begins at the first step after reload, and the first differing byte sits in the economy's double-precision region. One suspect — a private random stream — has been eliminated experimentally as the sole cause; the cause is not yet attributed and no fix is claimed. The owner unparked this investigation on 2026-11-02, rated it a crucial fix, and placed it first after integration completes. After it: WP-09 grows Development Mode into a full diagnostic environment in six increments.

Phase 0 · Route decided 2026-11-02

M2 — Windows verification path

The route is decided: (a) — the GitHub-hosted Windows runners already used by CI — extended into a scripted native test harness: build, launch, scripted scenarios, a save/load round-trip in the real save location, and automated frame capture with blank/size checks. The owner's own PC stays out until release. Cross-compilation alone will never be called verification.

Interim evidence (2026-11-02): the owner played a pre-adoption Windows build (0.5.4, built by the original author) for about an hour at Detroit — it launched and played correctly; its graphics looked somewhat low-resolution (presentation only; cause uninvestigated). Saves were not tested, and the current code's Windows build has never run natively — so this is provisional demonstration for an older build, not verification of the current one.

Gate: a recorded Windows session of the current code — launch, data and layouts found, gameplay, save/load — at a real airport layout.

Rules this map follows

  • Every milestone gets its own acceptance criteria before work starts; a milestone is complete only when its criteria pass with evidence.
  • Criteria are never weakened to obtain a pass; a blocked gate is documented, not walked around.
  • Nothing that already works gets rebuilt; nothing new is stacked on a known weak point until the weak point is fixed.
  • No delivery dates are invented; the milestone order is not silently changed.
  • Statuses update at milestone closeouts, from the development record.

Current position — updated 2026-11-01 (dated correction)

Next: the AirportSim engine

The owner revised the order of work after M1 was accepted. The studio's unified website comes first; the next development phase after it is the AirportSim engine itself — beginning with an evidence-backed engine review package and a proposed first milestone, presented for review before any engine change is made. Development Mode follows only after the engine work reaches its explicitly accepted completion milestone. (This stage previously pointed to Development Mode as the next step; that earlier ordering is preserved in the project's records and in this page's own history — it is corrected here, not erased.) M2 below remains the next roadmap milestone in Phase 0 and is not displaced by this ordering.

Phase 2 · Planned

Depth of the living world

ATC final speed control (K7), parallel-runway operations, additional airport layouts together with the map-data decision (baked-in vs runtime fetching), and data-table/mod foundation work. These items are interdependent; their internal order gets set by evidence when the phase opens, not assumed now.

Phase 3 · Planned

The business game deepens

Contract terms, the staff interface, rival entities — and the own-airline feature (implemented today, never yet played through) earning its demonstrated grade. Each item is revalidated against the code and the intended gameplay before implementation.

↓

Phase 4 · Final gate

Polish and release readiness

Performance evidence (including the largest hubs, unmeasured today), stability and usability, a proven release pipeline, Windows release verification, and packaging. A release itself additionally requires the project owner's explicit approval — no approval, no release. Current builds are development builds; none is published.

Rules this map follows

  • Every milestone gets its own acceptance criteria before work starts; a milestone is complete only when its criteria pass with evidence.
  • Criteria are never weakened to obtain a pass; a blocked gate is documented, not walked around.
  • Nothing that already works gets rebuilt; nothing new is stacked on a known weak point until the weak point is fixed.
  • No delivery dates are invented; the milestone order is not silently changed.
  • Statuses update at milestone closeouts, from the development record.
